# MedMIG-CR InfoNCE E6 Hop8 + GRU Path Reranker Report

## Executive Summary

This run retrained InfoNCE MIND for `K=1`, `K=2`, and `K=3` with `6` epochs on the full DDXPlus v2 train queries, then evaluated retrieval with `max_hops=8`, `beam_width=64`, and `paths_per_interest=4096` on the 5,000-query comparison cohort.

Note: the tables in this report use `data/processed/comparison_cohort/new_queries.csv`, so they should be read as comparison-cohort results. For the official held-out DDXPlus v2 evaluation, use `data/processed/ddxplus_v2/test_queries.csv`.

The best baseline early-rank result is `K=1` with `MRR=0.3010` and `Recall@5=0.3836`. `K=3` gives the best baseline breadth with `Recall@50=0.4306`. After adding the post-hoc GRU path reranker to the `K=3` pipeline, early ranking improves substantially: `MRR` rises from `0.2948` to `0.3805`, and `Recall@5` rises from `0.3446` to `0.4218`. `Recall@50` stays unchanged at `0.4306`, which is expected because the reranker only reorders existing beam-search candidates.

## InfoNCE MIND Architecture

InfoNCE MIND maps a patient's evidence/seed nodes into one or more graph-space interest vectors.

Input:

- `seed_node_keys` from each patient query.
- These are mapped DDXPlus evidence/symptom nodes in PrimeKG, commonly `effect/phenotype|HPO|...` nodes.
- The model vocabulary contains `136` seed tokens including padding and unknown tokens.

Encoder:

- `ProjectedClinicalMIND`
- Symptom/evidence token embeddings are routed through the MIND capsule-style interest extractor.
- `K` controls the number of interest vectors:
  - `K=1`: one clinical search direction.
  - `K=2`: two search directions.
  - `K=3`: three search directions.
- Each interest vector is projected to the PrimeKG node embedding space.
- Graph embedding dimension is `64`.

Loss:

- The model is trained in graph space with contrastive InfoNCE.
- Target disease/effect nodes are positives for the target contrastive term.
- Evidence/seed nodes are positives for the evidence contrastive term.
- Other nodes in the target/evidence candidate sets act as negatives through the softmax denominator.
- The total loss combines:
  - target-node InfoNCE
  - evidence-node InfoNCE with `evidence_weight=0.2`
  - diversity regularization with `diversity_weight=0.05`
- Temperature is `0.07`.

| Valid CSV | `data/processed/ddxplus_v2/valid_queries.csv` |

## Beam Search and Candidate Generation

Retrieval is unchanged for baseline and GRU experiments. The reranker does not affect graph traversal.

For each patient:

1. Read `seed_node_keys`.
2. Resolve seed node keys to PrimeKG node IDs.
3. Run InfoNCE MIND to produce `K` interest vectors.
4. For each interest vector, run semantic beam search from the seed nodes.
5. Expand both incoming and outgoing graph neighbors.
6. Score each hop with the existing stateless score:

```text
step_score = alpha * cosine(neighbor_embedding, interest_vector)
             - beta * log(degree(neighbor) + 1)

path_score = sum(step_score over hops)
```

7. Collect candidate paths and candidate endpoint nodes.

Beam parameters:

| Parameter | Value |
|---|---:|
| `max_hops` | 8 |
| `beam_width` | 64 |
| `paths_per_interest` | 4096 |
| `alpha` | 1.0 |
| `beta` | 0.1 |
| `top_k` | 50 |

Positive and negative definitions:

- Positive path: endpoint is a disease node and endpoint is in that patient's `target_node_keys`.
- Negative path: endpoint is a disease node and endpoint is not in that patient's `target_node_keys`.
- Non-disease endpoints are not used for BPR training.
- Paths with invalid relation or direction IDs are dropped.

Candidate endpoint filter:

- Endpoint must be a disease node.
- Endpoint must be in the condition-map target universe.
- The condition-map target universe has `47` nodes total, including a few non-disease/effect nodes. The GRU reranker is deliberately a disease-path reranker, so it ranks disease endpoints only.

## GRU Reranker Architecture

The GRU receives one token per path hop. For a path:

```text
v0 --r1--> v1 --r2--> v2 ... --rL--> vL
```

the input sequence is:

```text
x1, x2, ..., xL
```

Each hop token is:

```text
x_t = concat(
  relation_embedding[r_t],
  direction_embedding[d_t],
  node_type_embedding[type(v_t)],
  projected_frozen_node_embedding[v_t]
)
```

Embedding components:

| Component | Description | Dim |
|---|---|---:|
| Relation embedding | Learned embedding for PrimeKG relation type | 32 |
| Direction embedding | Learned embedding for forward/backward traversal | 8 |
| Node type embedding | Learned embedding for coarse node type | 8 |
| Node embedding projection | Frozen PrimeKG node2vec embedding projected from 64 to 32 | 32 |

Node type vocabulary:

| Node type | ID |
|---|---:|
| anatomy | 1 |
| disease | 2 |
| drug | 3 |
| effect/phenotype | 4 |
| gene/protein | 5 |
| pathway | 6 |

GRU and scoring:

- 1-layer GRU
- Hidden dimension: `64`
- Dropout: `0.1`
- Final hidden state `h_L` represents the full path.
- A small linear head maps `h_L` to a scalar path score:

```text
h_L = GRU(x1, x2, ..., xL)
score(path) = Linear(ReLU(Linear(Dropout(h_L))))
```

The trained checkpoint is:

```text
artifacts/checkpoints/path_gru_reranker/infonce_e6_k3_hop8_gru_10k.pt
```

## GRU Training Objective

The reranker uses BPR pairwise ranking loss.

For each eligible patient, sample a positive path and a negative path:

```text
positive = path ending at target disease
negative = path ending at non-target disease
```

Then optimize:

```text
loss = -log sigmoid(score(positive) - score(negative))
```

Hard negative sampling:

- Negative paths are sorted by old additive beam-search score.
- Training samples negatives from the top `32` hard negatives for that patient.
- This makes the reranker learn against high-scoring wrong diseases rather than easy negatives.

Imbalance handling:

- The raw GRU dataset is highly imbalanced: `7,763` positive paths versus `190,266` negative paths.
- The model is not trained as a plain binary classifier over all rows, so the global negative count does not dominate the loss directly.
- Training first groups paths by `patient_index`.
- Only patients with at least one positive path and at least one negative path are BPR-eligible.
- Each BPR batch samples matched pairs:

```text
(positive_path_for_patient, negative_path_for_same_patient)
```

- This means every training comparison contains one positive and one negative path, rather than flooding the batch with all negative paths.
- The negative is sampled from the top-scoring hard negatives for that patient, so the model learns to beat plausible wrong disease paths.
- Patients with only negative paths are skipped for BPR because there is no positive path to compare against.
- This handles the main imbalance problem for pairwise ranking, though it does not yet do per-disease balancing or a held-out reranker validation split.

## How GRU Is Used at Test Time

The GRU reranker is inserted after beam search, not inside beam search.

Test-time flow:

```text
patient seeds
-> InfoNCE MIND K=3
-> beam search max_hops=8, beam_width=64
-> collect candidate paths
-> filter disease endpoint paths
-> GRU scores each path sequence
-> aggregate by endpoint disease using max path score
-> rank candidate diseases
-> evaluate MRR and Recall@K
```

The original additive score still controls graph exploration. The GRU only changes final candidate ranking. This is why `Recall@50` does not increase: the reranker cannot recover targets that beam search did not retrieve.

Implementation detail:

- `scripts/retrieval/run_ddxplus_infonce_gru_rerank.py` runs the original InfoNCE retrieval first.
- It converts each disease endpoint path into GRU input tensors:
  - `relation_ids`
  - `direction_ids`
  - `node_type_ids`
  - `dst_node_ids`
  - `path_len`
- It calls the trained GRU reranker to produce one scalar score per path.
- If multiple paths end at the same disease endpoint, it keeps the maximum GRU path score for that endpoint.
- It then explicitly sorts endpoint diseases by GRU score in descending order:

```text
ranked_candidates = sorted(endpoint_scores, key=score, reverse=True)[:50]
```

- The sorted endpoint list is written to `predictions.csv` with ranks.
- The evaluator reads those ranks and computes `MRR`, `Recall@5`, `Recall@10`, `Recall@20`, and `Recall@50`.

So the GRU does not magically sort paths internally. It gives a scalar score; the retrieval script uses that score to sort candidates.

## Notes and Limitations

- InfoNCE MIND was trained on the full train query file, but the GRU reranker was trained on only the first `10,000` train queries.
- The GRU is trained and evaluated as a disease endpoint reranker, not a general target-node reranker.
- The condition map contains a small number of non-disease target nodes. The baseline retrieval can emit any node in the target universe, while the GRU reranker currently filters to disease endpoints. This makes the GRU experiment clinically focused, but the candidate set is not perfectly identical to the baseline.
- The GRU reranker uses frozen PrimeKG node embeddings and learned relation/type/direction embeddings. It does not retrain graph embeddings.
- Current GRU validation is pairwise training accuracy on sampled BPR pairs, not a held-out reranking validation set. A future run should add a validation split for early stopping.
- Since the reranker operates post-hoc, improvements concentrate on ranking metrics such as `MRR` and `Recall@5`; broad recall cannot exceed candidate coverage from beam search.
